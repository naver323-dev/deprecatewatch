# DeprecateWatch 공통 AI 작업지침서 (v1.2 · 2026-11-18)

> 이 문서는 **피클(Pickle) · 제미나이(Gemini) · 그록(Grok)** 중 어떤 AI가 이 프로젝트를 이어서 작업·검수하더라도
> 같은 원칙과 같은 규격으로 움직이게 하기 위한 단일 기준서입니다. 작업 전에 이 문서를 먼저 읽고, 규칙이 바뀌면
> 이 문서를 먼저 고친 뒤 코드·사이트를 고칩니다.

---

## 1. 프로젝트 목적

- **한 줄 정의:** SDK·런타임·프레임워크·DB·OS·클라우드 서비스의 **지원종료(EOL)·디프리케이션 날짜를 정적 표와 JSON으로
  제공하는 아카이브**. "이 버전 아직 지원되나? 언제 끝나나?"라는 질문에 **날짜가 붙은 값**으로 답하는 것이 목적입니다.
- **왜 필요한가:** AI 모델의 학습 컷오프 때문에 "Node.js 18은 아직 LTS"처럼 과거 정보로 답하는 오류가 흔합니다.
  공식 소스에서 매일 다시 받아 `as_of` 날짜를 붙여 두면, AI 검색·에이전트가 인용할 수 있는 신선한 근거가 됩니다.
- **타깃:** 영어권 개발자·SRE·보안 담당자, AI 검색(ChatGPT·Perplexity·Gemini·Claude) 인용.
- **비즈니스 연결(장기):** 개발자 대상 뉴스레터, 마이그레이션 템플릿, GitHub Sponsors. 첫 수익까지 4~6개월 예상.

## 2. 절대 원칙 (예외 없음)

1. **무과금:** Cloudflare Pages 무료, GitHub 공개 저장소, 공개 API·피드만 사용. 유료 API·유료 플랜·키 발급 필요 서비스 금지.
2. **실명·신분 비노출:** 실명, 핸들, 군 관련 정보(소속·직책·군 프로젝트명·DTIS/RADAR 등), 개인 연락처를
   사이트·저장소·문서·커밋·메타데이터 어디에도 쓰지 않는다.
3. **날짜는 원문 그대로:** 추정·보간·수기 입력 금지. 원문에 없으면 `not announced` 또는 `no-eol-date`로 표시한다.
4. **벤더 평가 금지:** 순위·점수·추천·비교 우열을 만들지 않는다. "지원 중인 최신 사이클"과 "원문이 밝힌 대체"만 사실로 적는다.
5. **규정 먼저:** 데이터 라이선스·이용약관(endoflife.date MIT, 벤더 문서 인용 범위)을 확인하고 출처 링크를 유지한다.
6. **광고·추적 최소:** 수집 스크립트는 GA4 하나뿐. 광고·제휴·리마케팅 태그 금지(현재 0개).

### 4.2 정규화 스키마 (`data/eol_normalized.json` → `/api/eol.json`)
```
schema_version, generated_at, as_of, timezone,
counts {products, cycles, eol_cycles, eol_with_date, eol_without_date, upcoming_eol_365d, lambda_runtimes, announcements},
definitions {supported, security-only, eol, eol-with-date, eol-no-date, no-eol-date},
license, attribution,  (제품/upcoming/announcements JSON은 sources[] 도 함께)
sources[],
products[] {slug, name, category, tags, cycle_count, latest_cycle, latest_version,
            current_status, current_eol, current_support_end, active_cycle,
            soonest_eol {cycle, eol, days_left}, eol_cycle_count,
            cycles[] {cycle, release_date, support_end, eol, eol_status, eol_date_published, latest,
                      latest_release_date, lts, extended_support, replacement, link, days_left}},
upcoming[] {slug, name, category, cycle, eol, days_left},
lambda_runtimes[] {name, identifier, os, deprecation_date, block_create, block_update, status, days_left},
announcements[] {source, source_label, date, title, product, kind, summary, url}
```
- 상태 규칙: `eol`(종료일 경과 **또는** 원문이 종료로 표시했지만 날짜 미공개) / `security-only`(활성 지원 종료, EOL 전) /
  `supported` / `no-eol-date`(원문에 EOL 없고 종료 표시도 없음).
  상태는 **오늘 날짜와 원문 날짜 비교로만** 계산한다(같은 스냅샷이면 항상 같은 결과).
- **eol 대표 숫자 규칙 (v1.2에서 고정):** `counts.eol_cycles`는 합계(7,481)이고, 그 안을
  `eol_with_date`(6,928)와 `eol_without_date`(553, 원문 `eol=true`+`eolFrom=null`)로 나눈다.
  문구·표·llms는 **"past their published EOL date 6,928 + marked end of life with no published date 553"**처럼
  반드시 나눠 쓴다. 합계를 "past their EOL date"라고 단정하지 않는다. 사이클별로는
  `eol_date_published`(bool)로 판별하고, 표에서는 종료일 대신 `date not published`로 렌더한다.
- **API 메타데이터 (v1.2):** `/api/eol.json`·`products.json`·`upcoming.json`·`announcements.json` 모두
  `license`·`attribution`·`sources[]`를 갖는다. 새 API를 추가하면 같은 3개 필드를 넣는다.
- 스키마를 바꾸면 `schema_version`을 올리고 **`/llms.txt` 설명도 같은 커밋에서** 갱신한다(API 계약 문서 역할).

## 5. GEO(AI 검색 최적화) 규칙 — 새 페이지를 만들 때도 반드시 유지

1. **JS 없이 읽히는 정적 HTML.** 표·수치는 서버에서 렌더한다. 스크립트는 GA4만.
2. **clean URL.** Cloudflare Pages는 `.html` 요청을 308로 확장자 없는 URL에 넘긴다. 링크·canonical·sitemap·JSON-LD의
   URL은 반드시 확장자 없는 형태(`/product/nodejs`)로 쓴다. `scripts/build_site.py`의 `public_urls()`가 최종 HTML에서
   한 번 더 정리하므로, 새 링크도 이 함수를 거치게 둔다.
3. **JSON-LD:** 허브는 `Dataset`(dateModified=해당 페이지 lastmod, distribution 3종) + `WebSite` + `Organization` + `FAQPage`,
   제품/목록 페이지는 `WebPage` + `FAQPage`(또는 `CollectionPage`+`ItemList`). **화면에 보이는 FAQ 문장과 JSON-LD 문장은
   같은 원본에서 생성**해야 하며, 검사 스크립트가 일치 여부를 확인한다.
4. **`/llms.txt`:** H1 + blockquote 요약 + 엔드포인트·페이지 패턴·정의·출처·인용 방법·한계. 수정 시 여기도 갱신.
5. **`/robots.txt`:** GPTBot·OAI-SearchBot·ChatGPT-User·ClaudeBot·Claude-Web·PerplexityBot·Perplexity-User·
   Google-Extended·Applebot-Extended·CCBot 등 명시 허용 + Sitemap 라인.
6. **`sitemap.xml`:** 모든 페이지. `lastmod`는 **빌드일이 아니라 그 페이지 데이터가 마지막으로 바뀐 날**(v1.2).
   `data/site_state.json`이 페이지별 데이터 지문(sha256)과 그 지문이 마지막으로 바뀐 날짜를 보관하고,
   `build_site.py`의 `note_mod()`/`mod_of()`가 sitemap과 JSON-LD `dateModified`에 같은 값을 쓴다.
   지문에는 `as_of`·생성시각·"in N days" 같은 매주 바뀌는 값을 넣지 않는다(넣으면 전 페이지가 매주 '변경'이 된다).
   이 파일은 스냅샷과 함께 커밋해야 다음 주 실행에서 날짜가 이어진다.
7. **신선도 표기:** 모든 표·페이지에 `as_of`(2026-11-18 형식)를 노출하고, 인용 시 함께 쓰라고 안내한다.
8. **페이지당 하나의 질문에 직접 답하기:** 제품 페이지 첫 문단과 "Direct answer" 박스는 그 제품의 현재 사이클 기준
   EOL/지원 상태를 데이터로만 서술한다.

## 6. 파이프라인과 자동화

```bash
python3 scripts/fetch.py        # 1) 모든 소스 원문 수집 → data/raw/ (캐시, REFRESH=1이면 재수집)
python3 scripts/normalize.py    # 2) data/raw → data/eol_normalized.json
python3 scripts/build_site.py   # 3) 정규화 데이터 → site/ (HTML 530 + api/*.json + llms.txt + sitemap)
python3 scripts/check_site.py   # 4) 검증(실패 시 exit 1 → 배포 중단)
python3 scripts/build_all.py    # 위 4단계 일괄 실행
```
- **자동 실행:** GitHub Actions `daily-eol-refresh` (`.github/workflows/update.yml`) — **매주 화요일 06:00 KST**
  (월요일 21:00 UTC, `cron: 0 21 * * 1`), `workflow_dispatch` 수동 실행 가능.
- **문구 동기화 완료(2026-11-18):** 홈 FAQ·JSON-LD Dataset·about의 "daily" 문구를 "weekly (Tuesdays 06:00 KST)"로
  `scripts/build_site.py`에서 수정하고 재빌드(530페이지)·`check_site.py`(88,877건 PASS)·푸시·Pages 배포까지 확인했다(커밋 8a9cf22).
  앞으로 갱신 주기를 바꾸면 이 문구와 `feed.xml` 설명을 같은 커밋에서 고친다. 수집→정규화→빌드→검증→변경분 커밋·푸시 → Cloudflare Pages 자동 배포.
- **커밋 대상:** `data/eol_normalized.json data/products_v1.json data/site_state.json site` (v1.2에서 `site_state.json` 추가).
- **주의:** 이 저장소의 GitHub App 토큰에는 `workflows` 권한이 없어 **워크플로 파일은 git push로 올릴 수 없다**
  (`refusing to allow a GitHub App to create or update workflow`). 워크플로를 수정할 때는 GitHub 웹 UI의
  "Add file → Upload files"로 `.github/workflows/` 경로에서 업로드한다(웹 편집기에서 직접 타이핑하면 자동 들여쓰기로
  YAML이 깨진 사례가 있었음).
- 로컬 실행에는 파이썬 3.11+ 표준 라이브러리만 필요(외부 패키지 0).

## 7. 수정할 때 (버전 전파 규칙)

1. **문구·레이아웃:** `scripts/build_site.py` (`CATEGORY_LABEL`, `CSS`, 각 `build_*` 함수).
2. **설정값:** `data/site_config.json` — `base_url`, `ga_id`, `contact`. GA4 ID를 바꾸면 `privacy.html` 문구도 자동 반영된다.
3. **소스 추가·제거:** `scripts/fetch.py`의 상수와 `scripts/normalize.py`의 파서, 그리고 `DOC["sources"]`·`about`·`llms.txt`
   세 곳을 **같은 커밋에서** 갱신한다(출처 표기가 한 곳만 바뀌면 신뢰가 깨진다).
4. **검증 통과 필수:** `python3 scripts/check_site.py`가 PASS여야 푸시한다.
   교차검수 반영(v1.2)으로 추가된 검사: `counts.eol_cycles == eol_with_date + eol_without_date`,
   `eol_date_published == bool(eol)`, 종료일 없는 eol 행의 `date not published` 표기, 제품 description이
   문장부호로 끝나고 괄호 뒤에 문장이 붙어 있지 않을 것, sitemap `lastmod`가 `site_state.json`과 일치할 것,
   모든 API에 `license`·`attribution`이 있을 것. 검사를 느슨하게 만드는 변경(금칙어 목록 축소,
   FAQ 일치 검사 제거 등)은 하지 않는다.
5. **규칙이 바뀌면:** 이 `00_작업지침서.md`의 버전을 올려(v1.0 → v1.1) 함께 갱신하고, 같은 폴더에 변경 요약을 남긴다.
6. **비밀 목록 위생:** 검사 스크립트의 금칙어(실명·군 등)는 **저장소에 커밋하지 않는다.**
   `data/forbidden_private.txt`(로컬, `.gitignore`) 또는 `FORBIDDEN_EXTRA` 환경변수로 읽고, 저장소에는 일반 규칙
   (이메일 도메인, 자리표시자)만 둔다. GitHub Actions처럼 비밀 목록이 없는 환경에서는 이메일·구조 검사만 돈다.
7. **다른 AI가 이어받을 때:** ① 이 문서 → ② `README.md` → ③ `scripts/build_site.py` 순으로 읽고, 실측 수치는
   `data/eol_normalized.json`의 `as_of`·`counts`에서 확인한다(문서에 적힌 수치는 그날의 스냅샷이다).

## 8. 하지 말 것 (검사 스크립트가 자동 차단)

- `G-XXXXXXXXXX`, `TODO:` 같은 자리표시자.
